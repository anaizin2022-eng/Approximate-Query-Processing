⚡ Welford's Method

只保存 3 個數字 (N, Mean, M2)，不存任何原始資料。每次新值進來就用遞迴式更新，記憶體永遠是 O(1)，而且數學上完全等價於對全部資料重新計算！

Online AlgorithmO(1) SpaceNumerically Stable

📊 Count-Min Sketch

3 個 Hash Function 對應 3 行格子，每個新物件同時更新 3 個格子。查詢時取 3 格中的「最小值 (Min)」，這個最小值一定 ≥ 真實次數，是最精準的上界估算！

ProbabilisticSub-linear SpaceAlways Overestimate

🔮 t-Digest & Approximate Histogram

將數百萬個值壓縮成幾百個「質心 (Centroid)」。關鍵在於它不是均勻壓縮——兩端 (P1, P99) 用超小的質心精細表示，中間 (P50) 則用大質心粗略表示。這讓極端值的估算精準度遠高於中位數，完美符合實際需求。BigQuery 和 Spark 的 approxQuantile 都基於此原理！

⚡ 深入理解 Welford's Method

直覺上計算平均數，我們會用 Sum ÷ N。但這需要儲存所有資料，或至少記住 Sum（大數相加會有浮點數誤差）。

Welford (1962) 發現了一個神奇的遞迴等式：

新值到達：x
δ₁ = x − Mean_old
Mean_new = Mean_old + δ₁ / N
δ₂ = x − Mean_new
M2_new = M2_old + δ₁ × δ₂

取樣變異數 σ² = M2 / (N−1)

這個公式數學上完全等價於重新用全部資料計算，且比累加 Sum 更穩定（不會因大數相加而失去精度）。只需 3 個變數！

應用場景： 資料庫的 Online Statistics、Spark Streaming 的即時指標、監控系統的 rolling mean。

📊 Count-Min Sketch 的碰撞原理

假設有 3 個 Hash Function，每個 Function 把物件映射到 5 個格子中的一個並累加計數。

問題： 不同物件可能被映射到「同一個格子」（碰撞/哈希衝突），造成格子數值被高估。

天才解法： 同時用 3 個不同的 Hash Function 映射到不同的行。雖然每行都可能有碰撞，但 3 個格子全部同時碰撞的機率極低。

查詢物件 x 的頻率：
h₁(x)=col_a, h₂(x)=col_b, h₃(x)=col_c
估算頻率 = MIN(table[0][a], table[1][b], table[2][c])

保證：估算值 ≥ 真實值（只高估，不低估）

記憶體只需要 3 × 5 = 15 個整數，不管流進來多少種物件都不會增加！

應用： Twitter 熱門話題統計、網路封包頻率分析、資料庫 JOIN 優化的 Bloom Filter 變體。

🔮 t-Digest 的質心壓縮

找精確 P99 需要對所有資料排序，是 O(N log N) 的問題。對串流資料根本做不到。

t-Digest 的想法： 把相近的值「揉」成一個質心 (Centroid)，記錄 (平均值, 筆數)。

質心 C_i = (mean_i, count_i)
整體資料 ≈ {C₁, C₂, ..., C_k} （k << N）

壓縮比例函數 q (百分位)：
兩端 q→0 或 q→1：質心 count 極小（精細）
中間 q→0.5：質心 count 可以很大（粗略）

這個「兩端精細，中間粗略」的特性，讓 P99/P1 的估算誤差遠小於 P50，完全符合工程實際需求（我們更在意極端情況！）。

應用： Google BigQuery 的 APPROX_QUANTILES()、Apache Spark 的 approxQuantile()、Prometheus 的 histogram_quantile 都是類似原理。
